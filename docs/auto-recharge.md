# 自动充值：运行机制与维护

[返回启动指南](../README.md) · 技术交流 QQ 群：**48878665**

本文面向管理员和维护人员。首次部署请先阅读 [README 的自动充值配置](../README.md#4-可选开启自动充值)。

## 站内确认与二维码

「立即充值」只打开确认弹窗。点击「提交订单」后，前端先调用 `POST /api/recharge/orders` 创建本地订单，传入套餐、渠道和随机 `request_id`。同一用户/请求号重复提交返回同一订单，套餐和渠道不可更换；金额与到账额度由后端配置决定。

再调用 `POST /api/recharge/orders/:id/checkout`，服务端签名 POST `/mapi.php`。渠道返回原生 `qrcode` 时，前端在本地生成二维码；返回 `payurl` 时，后端仅允许访问配置网关的 HTTPS 同源地址，提取 `#qrarea` 中的二维码图片并校验图片格式、大小，再返回图片数据。禁止嵌入第三方页面、跟随跨域跳转或把商户密钥发送给浏览器。

服务端在调用渠道前持久化下单状态，多个窗口并发也只允许一次创建请求。超时、断网、进程中断后的模糊结果通过 `/api.php` 查询**原商户订单号**恢复；不会再次盲目调用创建接口。已创建但图片获取失败时，仅重取原二维码。无法查明结果时保留待确认状态，由管理员核对，不假定付款失败。

`GET /api/recharge/orders/:id` 只读当前状态和缓存二维码；前端每 3 秒查询一次，到账或过期后停止，最多持续约 10 分钟。关闭弹窗会取消浏览器请求与定时器。继续支付沿用原订单，旧版跳转订单也先查单恢复。二维码只用于支付，前端状态或返回页面均不能触发加余额。

## 仅更新扩展页面和 API

已有服务运行时，先进入本项目目录。`docker compose` 不可用的服务器，把下面的命令替换为 `docker-compose`：

```bash
git pull --ff-only
docker compose build api ui
docker compose up -d --no-deps api ui
```

如有 `compose.production.yml`，继续使用原部署的 `COMPOSE_FILE` 环境配置，或在每条 Compose 命令中加 `-f docker-compose.yml -f compose.production.yml`。这些命令仅更新本扩展的 `api`/`ui`，不需要停止官方 Sub2API、官方数据库/Redis，或扩展的数据库/Redis。新字段自动加在扩展订单表上，不修改官方源码或官方表结构。

## 入账和日志

所有扩展业务代码均在本仓库内，不依赖修改或重新构建官方镜像。
启用后，服务在**官方数据库**中新建带 `sub_adds_recharge_` 前缀的订单和日志表；
订单表、`users.balance` 增量更新、官方 `redeem_codes` 已使用记录、入账日志在同一 PostgreSQL 事务提交。
官方兑换记录中的 `RA...` 号就是充值订单号（32 字符）。不修改官方表结构。
数据库连接账号需要创建这些扩展表/索引，以及读取 `users`/`api_keys`、更新用户余额、写入 `redeem_codes` 的权限。
首次启用前请备份数据库，并用与生产相同版本的官方实例验证字段兼容性。

回调按网关提供的 MD5 规则对原始参数排序验签，拒绝重复参数，并核对商户 PID、成功状态、支付方式、订单号和流水。首次入账必须通过服务端带商户凭证的 POST 查单，确认 `code=1/status=1`、订单归属、支付方式和唯一流水，不能信任前端“支付成功”、截图或请求中的金额。

### 按实际付款自动入账

**用户付款要求：支付金额必须与下单金额一致，否则无法自动到账。** 修改扫码后的付款金额可能导致渠道无法匹配订单，也就不会发出支付成功通知。已付款未到账时，应保留交易单号联系管理员，由支付平台核对收款归属，不能凭用户自报金额或浏览器显示直接补余额。

以下是渠道已经匹配订单并确认支付成功后的服务端结算规则，不代表渠道支持修改金额付款。

使用当前网关查单响应的 `price` 作为实际付款金额（人民币），`money` 作为平台返回的金额信息做有效性校验；不再要求它们等于原订单价格。只有确认已支付且 `price > 0` 才入账。未付款、零实付不加余额；缺失、负数、格式无效、订单或流水不符仍拦截并记录异常。对接其他网关时须先确认 `price` 的实际含义，不可把商户手续费余额或用户提交的字段当成实付金额。

到账额度 = **渠道查单确认的实付金额 × 订单创建时的套餐额度 ÷ 订单创建时的套餐价格**。计算使用 PostgreSQL `numeric`，截断保留 8 位小数，不用浮点数，不向上舍入。默认人民币/额度比例为 1:1，以下为渠道已确认收款的结算计算示例（不是用户付款指引）：

| 应付 | 渠道实付 | 自动增加 API 额度 |
| --- | --- | --- |
| ¥1.00 | ¥0.01 | $0.01 |
| ¥1.00 | ¥1.00 | $1.00 |
| ¥1.00 | ¥1.25 | $1.25 |
| ¥1.00 | ¥0.00 或未确认 | 不入账 |

自定义套餐按其下单时的比例折算。`amount_cents/credit` 保留原套餐报价，`paid_amount_cents/credited_credit` 单独保存实际结算；退款只扣回实际到账额度。日志同时记录应付、实付、实际额度和入账后余额。

每个订单仅结算一次。数据库事务锁定订单，`paid` 状态重复通知直接确认；网关流水全局唯一，跨订单重放导致整笔事务回滚。重复查单不追加余额；已结算后渠道金额变化会记录异常，而不会重复加款。Redis 刷新、官方充值记录和日志均不能成为再次入账的入口。
旧版已付款订单在升级时仅补齐实付与到账字段，不重新增加余额。不修改官方表结构。

### 用户可见范围

普通用户可查看自己的套餐、订单和到账日志。列表、单个订单、继续支付、查单均绑定官方登录身份，浏览器提交其他 `user_id` 无效。`/recharge/access` 从数据库复核管理员身份，普通用户看不到“充值管理”；即使自行请求管理接口，也会返回 403。管理员可查看全站订单和异常，管理默认显示“全部订单”；异常列表为空表示没有待处理异常，不代表没有订单。页面总览同时显示套餐、近期订单和日志，较多记录分页显示。

入账成功后清理官方 `billing:balance:<uid>` 和该用户 API Key 的 `apikey:auth:<SHA256>` 缓存，
并通过 `auth:cache:invalidate` 通知官方实例清理本地认证缓存。
Redis 失败不会回滚已收款入账；订单的 `cache_synced=false` 是持久重试队列，每 10 秒重试，
进程重启后继续处理。缓存任务携带余额变更版本号，避免退款与旧刷新任务并发时漏刷新。回调在数据库提交后返回纯文本 `success`，数据库失败时返回 `fail` 供网关重试。
缓存键和官方表字段依据本仓库对应的 Sub2API 版本，官方升级时应重新验证。

用户在「充值记录」「到账日志」查看自己的记录，运维人员可以在数据库查询完整日志：

```sql
SELECT o.id, o.user_id, o.amount_cents, o.credit, o.status, o.trade_no,
       o.paid_at, o.cache_synced, l.event, l.detail, l.created_at
FROM sub_adds_recharge_orders o
JOIN sub_adds_recharge_logs l ON l.order_id = o.id
ORDER BY l.id DESC;
```

## 查单补偿与异常管理

查单协议依据 [支付平台公开 API 文档](https://pay.1kexiu.xyz/docs/api)，使用服务端 POST `/api.php`，
`act=order/pid/key/out_trade_no` 放在表单正文，密钥不会进入 URL、浏览器或错误响应；禁止跟随重定向。
后台每轮最多查询 5 笔订单，按订单年龄采用 1 分钟、5 分钟、1 小时、1 天的间隔退避；
已入账订单继续核对 7 天，已退款冲正订单停止自动查单。查单调度与缓存重试独立运行，进程重启后从数据库恢复。
用户可在订单旁点「我已付款，查到账」，管理员可申请「查单补单」；同一订单两次主动查询至少间隔 15 秒。
查单失败不会假定未付款或增加余额。`status=2` 表示平台超时，**不是退款**，不据此自动扣回余额。
超时订单不再显示「继续支付」；如果平台后来确认付款，仍可正常接收回调并核对入账。

「充值管理」读取最近 200 条订单/异常。后台会重新检查登录用户在官方 `users` 表中的 `role=admin`、
`status=active` 和未删除状态，不信任浏览器声明的管理员身份。
管理员可查看金额差异、流水冲突、平台状态变化、连续三次查单失败、入账失败和缓存刷新失败，
填写原因后重新查单，或仅标记某条异常已处理。标记处理不会增加余额，也不绕过平台核对；异常再次出现会重新打开。
相同订单/异常类型合并计数，避免重复通知刷屏，所有管理员操作记录操作人 ID、原因和时间。退款请求审计独立保存，余额不足或事务回滚也不会丢失操作依据。

配置 `RECHARGE_ALERT_WEBHOOK_URL` 后，会 POST 以下结构；可选 `RECHARGE_ALERT_TOKEN` 作为 Bearer 鉴权。
不配置时仅在站内显示，不推送外部消息。推送失败持久重试，间隔由 1 分钟逐步增至最多 1 小时。
告警至少投递一次，接收端使用 `(issue_id, generation)` 去重；同一异常关闭后重开会产生新 generation。
不包含支付密钥、签名或原始网关响应。

```json
{"event":"recharge_exception","issue_id":1,"generation":1,"order_id":"RA...","kind":"payment_mismatch","detail":"支付金额字段无效，暂停入账"}
```

## 退款登记与余额冲正

公开文档没有退款接口；本模块**不会向支付平台发起退款**，也不提供未经核对的强制加款按钮。
管理员必须先在商户后台完成该订单的**全额退款**，再在充值管理里登记退款凭证、原因，并勾选确认。
服务在一个事务内锁定订单、检查余额足够、扣回该订单的实际到账额度，写入官方 `admin_balance` 负数调整记录、
退款凭证和操作日志，并安排缓存刷新。相同订单/凭证重复提交不会重复扣款；退款凭证不能用于多个订单。
原始付款回调在冲正后再次到达，也不会再次加款。
若用户已经消费额度、可用余额不足或用户已删除，整笔冲正不执行，记录异常，交由管理员处理资金与已消费额度；
不自动产生负余额。本版不支持部分退款，也无法从平台文档中的查单状态自动识别退款。
